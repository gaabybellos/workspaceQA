# workspaceQA

Runner-agnostic QA workspace for project discovery, reverse engineering, test case design, and future automation planning.

workspaceQA is built for QA engineers who want to plug in any project, understand how it works, document its modules, design traceable test cases, and only then decide whether to automate with a runner such as Playwright or Cypress.

## What It Is

workspaceQA is not a test framework.
It is a QA workspace that creates structure before automation.

It helps you:

- register or clone a target project;
- read the target project's README and source code;
- generate technical documentation from discovery;
- map modules, routes, components, endpoints, entities, risks, and test data;
- create a repository of requirements, test cases, and runner-agnostic specs;
- prepare a future automation architecture without installing a runner by default.

## What It Does Not Do By Default

The base workspace does not include:

- Playwright config;
- Cypress config;
- browser installation;
- runner workflows;
- generated automated tests;
- credentials or project-specific environment values.

Runner files should be created only after discovery, only for the selected project, and only in a future runner installation flow.

## Architecture

```text
workspaceQA/
  projects/                 target projects and cloned source code
  docs/
    technical/              discovery and reverse-engineering output
    standards/              documentation templates and standards
  test-case-repository/     requirements, cases, specs, and test templates
  scripts/                  workspace commands
  skills/                   reusable agent instructions
  .claude/agents/           Claude Code agent surface
  .opencode/prompts/        OpenCode agent surface
  .codex/agents/            Codex agent surface
```

## Folder Responsibilities

| Folder | Responsibility |
|---|---|
| `projects/` | Stores registered project metadata, README, and cloned source |
| `docs/technical/` | Stores documentation generated by discovery for each project |
| `docs/standards/` | Stores templates and documentation standards |
| `test-case-repository/` | Stores requirements, test cases, specs, numbering, and templates |
| `automation/` | Reserved for future runner-specific automation output |

`projects/` is intentionally clean.
It should not contain test cases, specs, runner configs, or automation code.

## Quick Start

```bash
npm run init-workspace
npm run register-project
npm run check-workspace
```

After registering a project, run the agent cycle:

```text
@discovery <slug>
@test-planner <slug>
```

Generation and execution are conditional:

```text
@test-generator <slug>  # only after a runner is installed
@test-runner <slug>     # only after tests exist
```

## Project Registration

`npm run register-project` asks for:

- project slug;
- display name;
- short description;
- base URL;
- repository URL or existing local source path;
- branch;
- project type.

If a repository URL is provided, the project is cloned into:

```text
projects/<slug>/source/
```

The generated project folder is:

```text
projects/<slug>/
  project.json
  README.md
  source/
```

## Discovery Output

The discovery agent reads:

```text
projects/<slug>/project.json
projects/<slug>/README.md
projects/<slug>/source/
```

It writes technical documentation to:

```text
docs/technical/<slug>/
  overview.md
  architecture.md
  source-map.md
  routes.md
  entities.md
  risks.md
  test-architecture-plan.md
  modules/
    <module>/
      README.md
      business-rules.md
      endpoints.md
      components.md
      test-data.md
      risks.md
```

## Test Case Repository

The test planner reads `docs/technical/<slug>/` and writes:

```text
test-case-repository/repository/<slug>/
  requirements/
  cases/
  specs/
  numbering.md
```

Templates live in:

```text
test-case-repository/templates/
```

Every test case uses:

```text
TC-<PROJECT>-<DOMAIN>-<NUMBER>
```

Example:

```text
TC-SHOP-CATALOG-001
```

## Agent Cycle

```text
qa-cycle
  -> discovery
  -> test-planner
  -> test-generator [requires installed runner]
  -> test-runner    [requires installed runner]
      -> bug-auditor
      -> test-healer
```

Rules:

- Discovery is mandatory.
- Test cases and specs stay runner-agnostic.
- Automation is optional.
- Runner-specific files do not belong in the workspace core.

## Commands

| Command | Purpose |
|---|---|
| `npm run init-workspace` | Validate and prepare the workspace structure |
| `npm run register-project` | Register a project and optionally clone its repository |
| `npm run check-workspace` | Validate required workspace files and registered project paths |
| `npm run new-spec` | Create a runner-agnostic spec scaffold |
| `npm run report` | Explain that reports are runner-specific until automation exists |

## Governance

Read `AGENTS.md` before changing agent behavior.
Read `docs/writing-standards.md` before editing docs, agents, scripts, or templates.

Agent definitions must stay synchronized across:

- `.claude/agents/`
- `.opencode/prompts/`
- `.codex/agents/`

## Portfolio Goal

This repository demonstrates a QA engineering workflow that starts with understanding the product instead of starting with a tool.

The intended flow is:

```text
source code -> discovery -> technical documentation -> test cases -> specs -> optional automation
```
